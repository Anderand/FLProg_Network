# Отчёт о работе: 24–26.09.2026

## Цель

Сделать один WebServer доступным через Wi-Fi STA, SoftAP и два независимых W5500 без трёх тяжёлых HTTP-контекстов и без ручной правки generated `.ino`.

## Выполнено

### Два W5500

- Проверены W5500 #1 (`.218`) и W5500 #2 (`.219`) на общей SPI-шине с разными CS.
- Подтверждены независимые MAC/IP, обнаружение обрыва каждого кабеля и восстановление после возврата линии.
- WZ2-01 завершён с `PASS=1`.

### Единый HTTP-сервер

- Добавлены shared listeners: один HTTP parser/context обслуживает несколько TCP listeners.
- Исправлена обработка W5500 `SYN_RECV`: первое HTTP-подключение больше не сбрасывается во время TCP handshake.
- Добавлена сериализация слушателей через один legacy HTTP context, что сохраняет RAM ESP8266.
- Устранён ранний выбор SoftAP вместо STA: при наличии Wi-Fi клиента основной маршрут — STA `.217`.
- Подтверждён доступ через `.217`, `.218`, `.219` и адрес SoftAP одновременно.

### Совместимость с обычным FLProg-проектом

- Исходный проект `ровки тест.flp` генерирует три legacy `WebServer` на один набор страниц.
- В библиотеке добавлено автоматическое объединение legacy WebServer одинакового порта в один HTTP-контекст.
- Первый сервер остаётся основным; остальные становятся shared listeners.
- Исходный FLProg-проект сгенерирован и прошит без ручной правки `.ino`: пользователь подтвердил работу.

### Поведение при отсутствии Wi-Fi

- Сервер может стартовать через доступный W5500, когда Wi-Fi-клиент недоступен.
- Появившиеся позже интерфейсы подключаются к тому же серверу.

## Проверенные результаты текущего этапа

- Одновременное открытие страниц через Wi-Fi STA, SoftAP, W5500 #1 и W5500 #2.
- Web восстанавливается после обрыва/возврата линий по ранее согласованным тестам.
- Обычный проект FLProg работает с библиотекой без редактирования generated-кода.
- При диагностике стабильного запуска: `listen=1`, `route=1`, `tcpError=0`, shared listeners подключены.
- Modbus TCP Slave на текущей библиотеке: пользовательская проверка PASS.
- TCP/UDP gate: STA TCP echo (`192.168.100.217:9101`) и STA UDP echo (`192.168.100.217:9102`) подтверждены реальным обменом. AP TCP/UDP listeners (`192.168.4.1:9101/9102`) успешно подняты; внешний AP-клиент недоступен, поэтому AP-часть принята как PASS по согласованию с пользователем.
- OTA service: аппаратный запуск подтверждён одновременно с общим HTTP и двумя W5500 (`ready=1`, `state=4`, `error=0`); `handleCount` стабильно растёт.
- NTP service: `pool.ntp.org` разрешён DNS, NTP-ответ получен, Unix-время обновляется; одновременно подтверждены STA+AP, общий HTTP и OTA. MQTT перенесён в пострелизный этап, так как в штатном FLProg отсутствует пользовательский MQTT-блок для проверки.
- Multi-transport HTTP failover: пользовательская аппаратная проверка PASS — отключение каждого W5500 по очереди не лишает веб-доступа через оставшиеся интерфейсы; после возврата кабеля доступ через соответствующий W5500 восстанавливается.
- Optical Architecture Gate: добавлена безопасная заглушка оптического транспорта. Она резервирует идентификатор и конфигурационный API, но по умолчанию выключена и не регистрируется как транспорт; текущий FLProg-проект успешно скомпилирован, прошит, а веб штатно открыт с ней. Аппаратная реализация отложена до выбора оборудования.
- KaScada через W5500 с `Pause=1 мс`: пользовательская проверка на текущей библиотеке PASS.
- Три цикла AP OFF/ON и короткий нагрузочный прогон с Web, Modbus и KaScada: PASS.
- Кросс-платформенная контрольная компиляция оптической архитектурной заглушки: RP2040, RP2350, STM32F1 и ESP32 — PASS через старый `arduino-builder`. Для STM32 устранена внешняя AVR-зависимость `avr/pgmspace.h` в `RT_HW_00_BASE`; создана переносимая обработка `PROGMEM`. ESP32: 33% flash и 10% RAM; RP2350: BIN, ELF и UF2, 1% flash и 2% RAM.

## Не объявлено пройденным

- Полная компиляция ESP8266 через `arduino-builder` была запущена, но зависла во внешнем сборщике; это не является PASS компиляции.
- RMII Web hardware и Optical hardware не выполнялись в этом этапе.
