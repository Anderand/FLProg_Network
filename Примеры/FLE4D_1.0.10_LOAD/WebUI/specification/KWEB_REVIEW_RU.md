# Разбор K-WEB для FLProg Network

Дата: 24.10.2026. Анализ предоставленных файлов, без установки библиотек, импорта в рабочий FLProg, запуска чужих скриптов или прошивки устройств.

## 1. Что изучено

| Материал | Содержимое и назначение |
|---|---|
| `K-WebV4.7.ubi` | XML пользовательского мультиблока: генерация C++, веб-элементы, сетевые настройки, база параметров, авторизация, файловый менеджер, OTA |
| `Пример_esp32.flp` | XML проекта FLProg с теми же определениями блоков и примером схемы; в дескрипторе указана ESP32 WROOM DEVKIT V1 |
| `K-WEBv19.zip` | Девять записей ZIP: папка и восемь заголовков K-WEB; Builder, Wi-Fi manager, файловые операции и встроенные Gzip-ресурсы |
| `K-WEB_Доп_lib.zip` | AsyncTCP 1.1.1, ESPAsyncWebServer 1.2.3, GyverDB 1.4.4 и её зависимости GTL, StringUtils, StreamIO, FOR_MACRO; также папка LittleFS с примерами и шрифтами |

В описании UBI прямо указан ESP32 core 2.0.17. Это данные данного комплекта; совместимость с другими версиями core в этом разборе не проверялась. Папка LittleFS в дополнительном ZIP не содержит `library.properties` и является набором примеров со шрифтами, а не полной независимой реализацией LittleFS.

Большие размеры `.ubi` и `.flp` — размеры XML редактора, включающего определения блоков, представление и подсветку кода. Это не расход Flash или RAM микроконтроллера.

## 2. Архитектура

`k-web.h` подключает WiFi, AsyncTCP, ESPAsyncWebServer, LittleFS, Update и DNSServer. Основная реализация ориентирована на ESP32; напрямую подменить ею наш backend STM32/W5500 нельзя.

`sets::Builder` собирает HTML, связывает элементы с переменными и сохраняет страницу в кэше. Числовой ID элемента формируется из адреса переменной, например `(uint32_t)&val`. Запись проходит через поиск ID в списке зарегистрированных связей; произвольный адрес из запроса напрямую не разыменовывается.

Интерфейс использует SSE: браузер создаёт `EventSource('/events')`, а `updateWD()` отправляет события `upd`, `prg`, `tm`, `led`, `seg`. Текстовые команды отправляются отдельным HTTP-запросом. В блоке есть проверки изменения значений перед вызовом updateWD.

Меню загружаются по требованию через отдельный запрос и затем помечаются загруженными. Последняя открытая вкладка сохраняется в localStorage.

### Частичная выдача и Gzip

В примере ответы создаются через callback `beginResponse(..., len, ...)`, который получает `maxLen` и `index` и отдаёт только очередную порцию. Такой принцип особенно полезен после нашего HTTP 500: большой ресурс не обязан целиком помещаться в очередь ответа.

Для нас нужен аналог поверх **FLProg_Network**, например ресурс из Flash с полной длиной, текущим смещением и ограниченной порцией отправки в `pool()`. Нужны корректное завершение при обрыве, таймаут, контроль ошибки записи и сохранение обслуживания FBD. Копирование синхронного цикла отправки большого файла вместо этого ухудшит отзывчивость.

Извлечённые Gzip-ресурсы K-WEB:

| Ресурс | В Gzip, байт | После распаковки, байт |
|---|---:|---:|
| Основной CSS | 4351 | 18372 |
| Основной JS | 8642 | 34014 |
| JS файлового менеджера | 2720 | 8552 |
| HTML авторизации | 1068 | 3209 |
| CSS авторизации | 1305 | 3743 |
| JS авторизации | 1643 | 5004 |
| Favicon | 344 | 605 |

Это измерения содержимого массивов в предоставленных заголовках, не результаты измерения памяти платы. **Сам по себе Gzip не отменяет наш лимит 2048 байта:** даже сжатые основной CSS и JS K-WEB больше него. Кроме того, текущему публичному HTTP API потребуется поддержка заголовка Content-Encoding. Нельзя просто заменить строку массивом Gzip и сохранить прежний sendProgmem.

### SSE и бюджет сокетов

SSE позволяет передавать изменение сразу, без очередного опроса. Но у нашего paged HTTP-адаптера сервер запускается с одним клиентским слотом, а ответы закрывают соединение. Постоянный event-stream займёт этот слот и может помешать загрузке ресурсов и командам.

Поэтому SSE нельзя включать простой заменой fetch на EventSource. Сначала нужны дополнительные слоты или отдельный транспорт, ограниченная очередь событий, обработка медленного клиента, восстановление снимка состояния после переподключения и проверка свободных сокетов W5500. Для текущего backend разумнее сначала улучшить существующий revision/since.

### Поля и удобство работы

У K-WEB есть проверка поля по regex, отправка при Enter/потере фокуса/после паузы 2 секунды, числовой spinner, цифровая клавиатура, настраиваемые индикаторы и рамки. Анимация прогресса работает в браузере через requestAnimationFrame.

Для нашего редактора это можно выразить параметрами descriptor: min/max/step, maxLength, единицы, режим подтверждения, текст ошибки, blocked/enabled. Проверка в браузере должна дополняться проверкой типа, диапазона и прав записи на контроллере.

## 4. Что не стоит переносить без переработки

### Кэш всей страницы

`k-web.h`, метод `page()`, вызывает `pageCache_.reserve(40000)`; вместе с ним существуют `html_`, `js_` и `renderedMenu_`. Это как минимум запрос на резервирование 40 КБ под один кэш плюс другие строки; фактическое успешное выделение и общий расход памяти платы не измерялись.

Для STM32 с 128 КБ RAM и для ESP8266 такая стратегия может оказаться слишком дорогой. Сохраняем нашу модель descriptor и небольших ответов. Частичная передача ответа полезна; полный динамический HTML-кэш не обязателен для неё.

### Связь элемента с адресом переменной

ID по адресу переменной удобен автору C++, но меняется при пересборке и раскрывает детали размещения памяти. У нас уже есть устойчивые CHANNEL и явные направления Publish/Command/Duplex. Их стоит сохранить, а не заменять указателями.

### Запись настроек при каждом изменении

В UBI встречается схема `db.set(...)`, затем `db.update()` при изменении настройки. GyverDBFile при update открывает файл на запись. При этом у самой GyverDBFile уже есть tick() и таймаут записи по умолчанию 10000 мс.

Стоит перенять разделение состояния и хранения, но использовать накопление изменений и отложенную запись. Для STM32 отдельно определяется физическое хранилище: оно не должно пересекаться с загрузчиком, приложением и staging OTA. Одним подключением ESP LittleFS это не решается.

### Авторизация и запись прошивки

Статический разбор выявил места, которые требуют отдельной проверки перед использованием:

- В извлечённых фрагментах UBI проверка checkAuth для `/ota` находится в финальном обработчике HTTP-запроса; коллбек загрузки вызывает Update.begin/write/end без собственной проверки доступа. Проверять доступ нужно **до первой записи**, а не только перед итоговым ответом.
- Аналогичное разделение присутствует у файловой загрузки в `k-ffs.h`: проверка есть в завершающем обработчике, а upload callback открывает и пишет файл. Нужен отказ до этих операций.
- Токен вычисляется детерминированно из пароля; ограничение неудачных входов находится в браузерном localStorage. Это не замена серверному ограничению попыток и управлению сроком сессии.
- Пароль авторизации передаётся параметром URL; изменения переменных и удаление файлов используют GET. Для нашего варианта предпочтительны явные операции записи, ограниченный размер тела, серверная проверка доступа и типов.
- JS обновления OTA в onload показывает OK без проверки HTTP-статуса и тела ответа. У нас должны различаться передача, проверка образа, принятие и подтверждённый запуск новой версии.

Это выводы по исходникам, а не результат атак на действующее устройство. Никакие запросы загрузки или записи не выполнялись.

### Зависимости и лицензии

Восемь файлов K-WEB не содержат найденного явного уведомления о лицензии, отдельный LICENSE в его ZIP отсутствует. У дополнительного AsyncTCP есть LGPL-3.0. До буквального переноса чужого кода нужно уточнить условия автора и каждого используемого компонента. В этом разборе сторонние исходники не добавлены в публичный репозиторий и релиз.

AsyncTCP/ESPAsyncWebServer из архива не нужны как обязательная зависимость нашего STM32/W5500 runtime. GyverDB со вспомогательными библиотеками имеет смысл рассматривать только как отдельную необязательную подсистему хранения, если собственный контракт хранения окажется недостаточен. Демонстрационные TFT-шрифты из папки LittleFS к нашему Web UI отношения не имеют.

## 5. Предлагаемый порядок работ

1. **Интерфейс:** статус online/offline/stale, понятное подтверждение записи, min/max/step/maxLength, Enter/Escape и ошибка у поля. Это даёт пользу без смены транспорта.
2. **Редактор:** контейнеры групп/рамок, адаптивные размеры, сохранение выбранной страницы, компактная диагностическая страница. Уже имеющуюся ленивую загрузку и revision/since сохраняем.
3. **HTTP-ресурсы:** отдельное API ограниченной передачи из Flash и генерация Gzip; оставить контроль полного размера для прежних bounded-ответов. Испытывать с разрывом соединения и медленным клиентом.
4. **Сохраняемые параметры:** общий контракт хранения и задержка записи, затем отдельные backend для поддерживаемых платформ.
5. **Позднее:** опциональный SSE и административные функции файлов/веб-прошивки с полноценной проверкой доступа. Поддержку ESP прошивки испытывать на отдельной согласованной плате.

Рабочие ESP .116/.117 и ожидаемый тест Generic STM32F407 в этом анализе не затрагивались. Наш код и опубликованный релиз не изменялись.

## 6. Как воспроизвести разбор

В этой рабочей папке сохранены инвентаризации ZIP, размеры сжатых ресурсов, извлечённые исходники и фрагменты XML. Они предназначены для локального просмотра. Оригиналы находятся в Downloads/Telegram Desktop. В `SOURCE_MANIFEST.json` зафиксированы SHA-256 исходных четырёх файлов.
