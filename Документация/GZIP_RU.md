# Gzip веб-ресурсов — проверка на FLE4D

25.10.2026. Проверено на FLE4D-30MT / STM32F407VG / W5500,
STM32 core 3.0.0, профиль FLProg_FLE4D_30MT_OTA, оптимизация -Os,
приложение с 0x08010000. Одинаковый скетч и descriptor теста 1.0.7;
отличаются режим статических ресурсов и необходимая обработка заголовка.

| Показатель | Обычная сборка | Gzip | Разница |
|---|---:|---:|---:|
| Flash по компилятору, байт | 137040 | 130856 | −6184 |
| Статическая RAM, байт | 16112 | 16112 | 0 |
| Полный BIN, байт | 137524 | 131340 | −6184 |
| Тела 15 статических ресурсов, байт | 17063 | 9560 | −7503 |

Экономия Flash — около 4,5%, объёма статических ресурсов — около 44%.
Размер ресурсов не равен размеру прошивки: обработчик gzip и согласование
заголовков тоже занимают Flash. Числа RAM — статические данные из отчёта
сборки, не пик heap/стека во время выполнения. Запас RAM для локальных
данных по этому отчёту — 114960 байт в обоих вариантах.

## Реализация

- `tools/build_gzip_assets.py` создаёт повторяемые gzip-массивы из обычных
  ресурсов. На микроконтроллере компрессора нет; распаковывает браузер.
- `FLPROG_WEBUI_GZIP_ASSETS=1` выбирает сжатые ресурсы, `=0` — обычные.
  По умолчанию оставлено 0 для совместимости; gzip включается флагом =1.
- Используются существующие публичные `print/write` и ограниченная очередь
  HTTP; нет синхронного цикла сетевой передачи, увеличения буфера или
  постоянного дополнительного массива RAM. Порционная выдача больших
  ресурсов прямо из Flash остаётся отдельной задачей.
- Успешный ответ содержит Content-Encoding: gzip, точный Content-Length,
  Vary: Accept-Encoding и Connection: close. Все ответы укладываются
  в 2048 байт вместе с заголовками; число маршрутов не изменено.
- При отсутствии Accept-Encoding gzip допустим. При явном запрете или
  отсутствии gzip среди разрешённых кодировок возвращается HTTP 406.
  Несжатая копия каждого ресурса в gzip-BIN не хранится, иначе пропадёт
  значительная часть экономии Flash. Для клиентов без gzip нужна сборка =0.
- В FLProg_Network для gzip-сборки добавлено сохранение Accept-Encoding
  при заполнении таблицы необязательных заголовков. Используется существующий
  слот, RAM таблицы не увеличена. Слишком длинное значение отклоняется
  консервативно через identity/406, вместо потери запрета gzip.

## Проверки

1. 25 автоматических Python/Node-тестов проходят, включая точную распаковку
   всех массивов и существующие проверки полей, команд и предпросмотра.
2. Скомпилированный C++-тест обработчика: бинарные NUL-байты, длины,
   Content-Encoding, Vary, q=0, wildcard, HEAD и 406. Сам WebUI-адаптер
   регистрирует только GET: его прежняя политика HEAD не менялась.
3. С текущего ПЛК до обновления прочитаны 15 обычных ресурсов; все совпали
   с исходниками. Контрольная обычная сборка повторила размер Flash/RAM 1.0.7.
4. Gzip-BIN записан по OTA, контроллер автоматически перезапустился.
5. На ПЛК все 15 gzip-ресурсов распакованы и сверены с исходными байтами.
   Проверены заголовки, Content-Length, явный запрет gzip и переполненная
   таблица необязательных заголовков. Динамическое состояние остаётся JSON.
6. В браузере: связь, группы, уставка 25→30.5, подтверждение команды,
   busy=true/result=false → busy=false/result=true, счётчик 0→1.
   Ошибок JavaScript нет. Тест меняет RAM, физические выходы не переключает.

Для чистого сравнения сохранена строка версии 1.0.7-WEBUI1.7; gzip-вариант
отличается SHA-256 BIN и заголовком Content-Encoding, а не новой версией
в сканере. Другие платы аппаратно не проверены.

Исходники, BIN обоих вариантов, команды сборки, логи и HTTP-результаты
сохранены в E:\SAI\FLProg_Network\Прошивки_для_проверки\FLE4D_WEBUI_GZIP.
