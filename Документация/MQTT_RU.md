# MQTT: динамические подписки и блоки v0.2

В r15 снят прежний фиксированный предел в четыре фильтра. Таблица расширяется
при добавлении нового фильтра, по одному месту; при повторном фильтре не растёт.
По умолчанию `SUB_LIMIT=0`: число подписок ограничивает доступная RAM.
Пределы длины темы (127 байт), пакета (768 байт), MQTT 3.1.1/QoS 0 остаются.
TLS, QoS 1/2 и постоянная очередь сообщений в этой версии не добавлены.

## Установка

Обновите **FLProg_Network целиком** из этого комплекта, затем импортируйте три
файла из `Блоки_FLProg/MQTT` в пользовательскую библиотеку FLProg.
v0.2 имеет новые входы Core; старые экземпляры v0.1 замените с переподключением
входов. Старый C++ вызов control(network,...) сохранён для совместимости.
SPI, Ethernet и Wi-Fi настраивает существующий проект FLProg. Его сетевой
интерфейс должен регулярно выполнять pool(). MQTT-блок сам сеть не перенастраивает.
Один MQTT Core на проект, Publish и Subscribe можно использовать многократно.

## Core

| Вход | Значение |
|---|---|
| EN | Разрешение; фронт включает подключение и автоматическое восстановление |
| CON / DIS | Положительный фронт подключения / отключения; DIS имеет приоритет |
| NET_KIND | 1 — W5500, 2 — Wi-Fi, 0 — существующий реестр NetworkDevice |
| NET_NUM | Номер интерфейса FLProg 1..8; в режиме реестра его зарегистрированный ID 0..254 |
| SUB_LIMIT | 0 — динамическое расширение; положительное число — добровольный предел |
| Broker / Port | Имя или IP брокера, порт 1..65535 (обычно 1883) |
| ClientID | Непустой уникальный ID клиента |
| User / Password | Учётные данные брокера, могут быть пустыми |

Настройки применяются при фронте EN/CON. Изменив параметры, подайте новый
фронт CON. При ошибочной конфигурации старая сессия закрывается.
`Connected` означает MQTT-сессию; `Busy` — текущую протокольную операцию;
`ERR`/`Error` — диагностику, `State` — состояние клиента.
`Subscriptions` — число фильтров, подтверждённых SUBACK;
`SubBytes` — байты выделенной таблицы (без служебных данных аллокатора).
Во время восстановления подписок новый запрос может вернуть BUSY:
повторите его новым фронтом позднее.

## Subscribe и Publish

Subscribe: Topic — фильтр, например `home/+/temperature` или `home/#`;
положительный фронт Subscribe ставит запрос в очередь. Accepted — местное
принятие запроса, не SUBACK. Подтверждение видно по Subscriptions/ERR Core.
При BUSY=1 запрос автоматически не повторяется; подайте новый фронт позже.
Received выдаёт импульс при получении подходящего текстового сообщения;
RxTopic/Message/Retained содержат его данные. Это последнее сообщение за цикл,
а не очередь без потерь. Одновременные частые сообщения могут заменять друг друга.

Publish: фронт Send, Topic без +/#, Message и Retain.
Accepted означает принятие клиентом в отправку; QoS 0 не имеет подтверждения
доставки брокером. При занятости повторите фронт после освобождения клиента.
Не используйте Accepted как подтверждение выполнения команды оборудованием.

Пример: Core EN=1, NET_KIND=1, NET_NUM=1, SUB_LIMIT=0, Port=1883,
Broker=адрес вашего брокера, ClientID=уникальное имя ПЛК. Дождитесь Connected.
Подавайте фронты Subscribe для фильтров последовательно, после завершения
предыдущей операции. Пятый и последующие фильтры теперь принимаются.

## RAM, ошибки и жизненный цикл

На один сохранённый фильтр выделяется 128 байт при стандартной длине темы.
4 фильтра — 512 байт; 8 — 1024; 16 — 2048. До первой подписки таблица не
выделяется. Постоянные буферы MQTT и память String в эти числа не входят.
При ожидающем или отклонённом SUBACK возможно одно дополнительное место.
Увеличение таблицы иногда требует временно старый и новый участок RAM;
поэтому свободная память и её фрагментация влияют на доступный размер.

| ERR | Причина / действие |
|---|---|
| 1 | BUSY: повторить запрос позднее новым фронтом |
| 8 | Превышен размер пакета; это больше не ошибка числа подписок |
| 11 | Брокер отклонил подписку |
| 14 | Неверный/слишком длинный фильтр |
| 15 | Нет подключённой MQTT-сессии |
| 17 | Достигнут явно заданный предел SUB_LIMIT |
| 18 | Не удалось выделить RAM; сохранённые фильтры остаются |
| 19 | Core: выбранный сетевой интерфейс не найден |
| 20 | Core: отрицательный SUB_LIMIT или некорректный порт |

При разрыве сети подтверждённый список сохраняется и восстанавливается
по одному фильтру. end()/begin() также сохраняют список, как раньше.
Для его явного удаления в C++: mqtt.end(); mqtt.clearSubscriptions();
деструктор освобождает память. Нельзя копировать владеющий памятью клиент.
setSubscriptionLimit(N) задаёт необязательный предел во время исполнения;
снижение ниже уже подтверждённых/ожидающих фильтров отклоняется без потери списка.
Старый FLPROG_MQTT_MAX_SUBSCRIPTIONS теперь задаёт только начальный предел,
по умолчанию 0. Для настройки используйте метод, а не define только в .ino.

## Проверено в этом выпуске

Host C++: 300 фильтров, отсутствие переполнения счётчика после 255, дубликаты,
явный предел, изменение предела во время SUBACK, искусственная нехватка RAM
и повтор, отказ брокера, восстановление 301 фильтра, освобождение памяти.
Дополнительно 26 проверок HTTP/MQTT и 99 тестов WebUI/менеджера.
Три UBI разобраны как XML, их loop-код включён в скетч для STM32 F407 core 3.0.0.
Аппаратное испытание MQTT с реальным брокером в этой операции не проводилось.
ПЛК не перепрошивался; устройства .116/.117 не затрагивались.
