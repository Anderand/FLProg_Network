# ESP32 Universal0.5 — HTTP-чтение ПЛК без PC Bridge

## Состояние

Это кандидат, собранный для классическойESP32 WROOM/4MB, core3.3.11.
**На ESP не установлен.** Установленная Universal0.4, настройки Wi-Fi/NVS,
UART и FLE4D не менялись. Реальный ESP↔UART↔ПЛК не испытывался.

Добавлена универсальная сервисная страница `/plc` на порту настроек8080.
После будущей установки и подключения UART она сможет читать каналы через ESP
без запуска PC Bridge. Проект, модель, версия и значения не зашиты в ESP:
они берутся из ответа ПЛК. Это ещё НЕ выдача всего макета редактора изFlash.
Команд/записи/управления выходами в этом прототипе нет.

TCP↔UART на прежнем порту остаётся прозрачным для PC Bridge. Новая HTTP-часть
понимает только служебное HELLO, чтение значения и описания канала WebUI.
Modbus/MQTT, обновление прошивки через этот HTTP API и другие службы не реализованы.

## Владение UART

Один активный владелец: TCP или один HTTP-запрос. При подключённом TCP-клиенте
HTTP-запуск возвращает409, не перехватывает UART. Пока HTTP-запрос выполняется,
новые TCP-клиенты отклоняются. Для переключения закройте TCP-соединение PC Bridge.

UART-клиент кооперативный: до64байт RX и64байт TX за pool(), без ожидания ответа
в обработчике HTTP. POST запускает операцию и сразу возвращает202/ticket;
браузер затем читает результат. Таймаут1500мс, автоматического повторения нет.
Очереди операций нет. Результат один, заменяется следующим запросом; старый ticket
получает409. При потере сети незаконченный обмен отменяется, сеанс инвалидируется.
Уже отправленные байты UART нельзя отозвать, но здесь формируются только чтения.

## Доступ

Будущий адрес: `http://<IP_ESP>:8080/plc`. Сначала войдите на `/` паролем настроек
ESP. Используется существующий сеансовый cookie; POST также требует токен формы.
В режиме AP-настройки и без Wi-Fi HTTP-чтение отключено. Страница сама не запускает
обмен UART при открытии. Нажмите «Проверить ПЛК» либо «Прочитать».
На каждый запуск чтения создаётся свежий сеанс HELLO, затем читаются метаданные
и значение. Поддержаны bool/int32/float/text, номера0..255; защита каналов остаётся
на ПЛК. Вывод через textContent, не через HTML из ответа.

## Экспериментальный API

| Запрос | Результат |
|---|---|
| GET /plc-api/session | Токен формы; нужен вход |
| POST /plc-api/start | op=hello/read/meta,channel,token;202 и ticket |
| GET /plc-api/result?ticket=N | state,status,payloadHex без нового UART-запроса |

op=write и любые другие операции отклоняются. HTTP-параметры — form-urlencoded.
Состояния:0Idle,1Sending,2Waiting,3Done,4Timeout,5PlcError,6Cancelled.
status — код ответа протокола ПЛК; payloadHex — проверенный CRC полезный ответ
без байта status. Нет поля «PLC online» по одному TCP-порту или счётчику байтов.
Это отдельный предварительный API, ещё не замена полного PC API `/api/v1`.

## Проверки

1. Настоящие C++ клиент/сервер: дробление и короткие записи, бюджеты за проход,
   HELLO/read/meta, ошибочные/слишком длинные кадры, CRC, таймаут и переполнение
   millis(), отмена, новый сеанс, взаимное исключение сTCP. Команд записи0.
2. Настоящие ESP-обработчики HTTP на нативном WebServer-адаптере: cookie/token,
   отсутствие write, диапазоны каналов,409Busy, ticket, кэш результата без повторного
   UART-обмена, запрет вAP/безсети. Это не эмуляция всей Arduino/ESPплаты.
3. Та же HTML/JS-страница в браузере с нативными C++ обработчиками и виртуальным
   ПЛК: чтение101=25, повторный сеанс, отказ102, пустой номер, восстановление101.
4. Реальная компиляция ESP32: Flash947976,staticRAM47912. По сравнению с0.4:
   Flash+11432,staticRAM+376. Блок запроса376байт; страница хранится воFlash.
   Результат сериализуется ограниченной строкой до~650байт; WebServer также
   использует динамическую память. Динамический пик RAM на ESP не измерялся.
