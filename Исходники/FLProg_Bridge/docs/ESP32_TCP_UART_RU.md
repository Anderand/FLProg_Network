# История ESP32 Wi-Fi UART прототипа

Актуальная прошивка — [FLProg Bridge Universal](ESP32_UNIVERSAL_RU.md): одна для разных проектов ПЛК, Wi-Fi и UART настраиваются через страницу настройки и сохраняются в NVS. Ниже сохранено описание предыдущего прототипа с настройками в исходнике; для новой версии его шаги настройки не применяются.

Этап A: PC FLProg Bridge0.4 подключается к ESP по TCP, а ESP передаёт существующий бинарный протокол в UART контроллера. Локальный HTTP и интерфейс браузера пока обслуживает компьютер. Это ещё не автономный HTTP-сервер на ESP и не замена проверенного COM-моста.

Путь: браузер → localhost PC Bridge → Wi-Fi/TCP ESP32 → UART ПЛК. Сайт остаётся во Flash ПЛК, PC Bridge получает его по тому же протоколу с проверкой SHA-256 и кешированием. Modbus/MQTT через этот мост не реализованы.

## Подготовка будущего стенда

Прототип предназначен для классической ESP32, ядро3.3.11. Для C3/S3 и ESP8266 требуется отдельный выбор UART/пинов и проверка.

В FLProgBridgeEsp32.ino локально задаются WIFI_SSID/WIFI_PASSWORD, UART_RX/UART_TX и UART_BAUD. По умолчанию имя сети пустое: Wi-Fi и точка доступа не запускаются. Учётные данные в комплект не включены. Пины16/17 — пример для ESP32 без конфликта с периферией/PSRAM; перед подключением выбрать фактически свободные пины своей платы.

Соединять UART с общей землёй и совместимыми уровнями3,3В; TX ESP идёт к RX ПЛК и наоборот. Не подавать5В на сигнальные входы ESP. На ПЛК нужна прошивка Bridge. Не подключать одновременно второй источник TX к тому же RX.

Пользователь пока не предоставил свободную ESP32: никакая ESP не прошивалась. Рабочие устройства .116 и .117 не сканировались и не использовались.

## Запуск PC Bridge после аппаратной подготовки

В поле COM/TCP укажите tcp://<IP_ESP>:3234 и нажмите «Подключить». Поле скорости на PC относится к COM; скорость UART ESP задаётся в её прошивке и должна совпадать с ПЛК.

Командная строка:

```text
FLProg_Bridge.exe --tcp <IP_ESP>:3234 --no-browser
```

COM-порт компьютера при этом не открывается. Без явного адреса TCP-подключение не выполняется. Команды по умолчанию запрещены; для них нужны разрешение PC Bridge и политика ПЛК.

## Ограничения прототипа

Один TCP-клиент. Две очереди по64 байта, не более64 байт за проход в каждом направлении, неблокирующая отправка TCP и ограниченная запись UART. Очереди сбрасываются при отключении клиента; повторной передачи команд нет. Неактивное соединение закрывается через10с, стандартный PC Bridge посылает heartbeat. Новое соединение устанавливает новый сеанс.

Прототип не содержит TLS, аутентификации TCP и сохранения сообщений. Предназначен для отдельного стенда в доверенной локальной сети; не публиковать порт3234 в Интернет. Таймаут команды означает неизвестный результат, а не разрешение повторять её автоматически.

## Что проверено программно

Реальный C++ ограниченный relay: порядок, двусторонний обмен, занятый выход, короткая/нулевая запись и сброс очередей. Реальный UART-протокол на C++ контроллере через намеренно фрагментированный localhost TCP: HELLO, чтение, загрузка веб-пакета, новый сеанс и отсутствие повторной команды при таймауте. Это эмуляция TCP/UART-участка, не радиоиспытание ESP.

Классическая ESP32 собрана: Flash894832 байта, static RAM46936 байт. Эти числа не измеряют свободную heap после подключения Wi-Fi или пиковую нагрузку. BIN с пустой конфигурацией сети — контрольный, автоматически не прошивается.

Следующий этап: отдельная ESP на стенде, проверка реального Wi-Fi/UART и восстановления после потери сети. Затем можно проектировать HTTP API непосредственно на ESP, чтобы компьютер для работы браузера не требовался.
