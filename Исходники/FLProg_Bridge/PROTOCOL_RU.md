# UART-протокол FLProg Bridge v1 (предварительный)

Протокол не зависит от редактора, HTTP, Ethernet и платформы ПЛК.
Один клиент и один незавершённый запрос на UART. Все целые — little endian.

| Поле | Байт | Назначение |
|---|---:|---|
| version | 1 | 1 |
| service | 1 | 0 управление, 1 WebUI, 2 Modbus (прототип службы), 3 MQTT (резерв) |
| operation | 1 | Операция службы |
| flags | 1 | 0 запрос, 1 ответ |
| sequence | 4 | Возрастающий номер запроса в сеансе, начиная с 1 |
| session | 8 | Случайное ненулевое число, выбирает клиент при подключении |
| length | 2 | Число байт payload, не больше 256 |
| payload | 0..256 | Данные |
| CRC32 | 4 | CRC-32/ISO-HDLC, совместима с zlib.crc32, от заголовка и payload |

Весь кадр кодируется COBS и заканчивается нулём. Максимум 280 байт COBS + разделитель.
Нулевой байт перед первым кадром клиента сбрасывает оборванный ввод. Слишком длинный
кадр отбрасывается до следующего разделителя; пауза внутри кадра более 250 мс также
переводит приём в ожидание разделителя. Плохой CRC/версия/длина не исполняются.

Ответ повторяет service/operation/sequence/session. Первый байт payload — статус:
0 OK, 1 неверный запрос, 2 нет службы/операции, 3 нужен новый сеанс, 4 занято,
5 запрещено политикой, 6 повторный/устаревший номер. Остальные байты — результат.

## Сеанс

HELLO: service=0, operation=1, payload ASCII `FLPBRIDGE1` (10 байт).
Ответ JSON: `protocol:1`, массив реально подключённых `services`, объект `identity`
с projectId/model/firmware из приложения. Строка identity задаётся корректным JSON
при создании Server, имеет статическое время жизни и должна поместиться в ответ.
Одинаковый повтор HELLO не обнуляет номер уже обработанных команд.

После reset ПЛК session=0: старые команды отвергаются. После timeout клиент
закрывает логический сеанс; повторной отправки команды нет. Результат потерянного
ответа считается неизвестным. Новый HELLO и свежее чтение требуются явно.
Это не аутентификация и не шифрование: физическая UART-линия считается доверенной.

PING: service=0, operation=2, пустой payload в установленном сеансе; ответ OK.
PC проверяет связь не чаще раза в секунду, когда транспорт свободен. PING не
открывает новый сеанс и не повторяет команды. При пропадании ответа потребуется
явное переподключение; это не бесконечный цикл сетевых запросов из каждого прохода ПЛК.

## Служба 1: WebUI

- 1 READ: payload — uint8 номер канала. Ответ: тип + значение.
- 2 META: payload — номер. Ответ: номер, тип, направление, затем UTF-8 ID.
- 3 WRITE: номер, тип, значение. Ответ OK без данных означает очередь, не выполнение.
- 4 READ_BATCH: от 1 до 16 номеров каналов. Ответ начинается количеством
  возвращённых значений, затем идут записи `номер / длина / тип + значение`.
  В один кадр помещается только ограниченный префикс списка; клиент продолжает
  чтение оставшихся каналов отдельным запросом. Секреты не читаются.

Типы: 0 bool (1 байт 0/1), 1 int32 (4 байта), 2 IEEE754 float32 (4 байта),
3 текст (до 63 байт UTF-8, без нулевого терминатора). Направления: 0 publish,
1 command, 2 duplex. Command-only значения не читаются, чтобы не раскрывать секреты.
Системные номера 0..100 защищены от записи. Пользовательские 101..255 используют
тот же fbdIndex, что и блоки FLProg; отдельной нумерации мост не вводит.

Запись требует включения на PC и callback-политики в ПЛК. Callback проверяет
разрешённые выходы, диапазоны и busy проекта; без callback адаптер только читает.
Дополнительно отвергается запись поверх команды, ещё не забранной блоком.

## Ограничение нагрузки

Server.pool(port, millis(), 64) вызывается каждый цикл и читает/пишет не более
64 байт в каждом направлении за вызов. Нет delay/flush/ожидания ответа.
Port должен иметь неблокирующие available/read/availableForWrite/write.
Обработчик службы также обязан быть коротким и не ждать сеть/оборудование.
Три фиксированных буфера занимают 839 байт, плюс поля/регистрация служб/выравнивание.
Это добавочная RAM; не заявляется нулевой расход памяти. На F407 размер Server
проверяется в отчёте сборки; нет динамического выделения внутри ядра протокола.

Полный веб может быть получен из Flash ПЛК через службу4 (см.docs/FLASH_WEB_RU.md); PC Bridge кеширует проверенный пакет, ESP0.6+ передаёт его браузеру. Через UART проходят ресурсы, значения и команды. ID проекта, версия
Web API и SHA-256 ресурсов должны совпасть с HELLO контроллера. Изменение макета
требует нового экспорта и пересборки прошивки с соответствующим `_bridge.h`.
Автовосстановление создаёт новый сеанс; отложенные команды не повторяются.
