- 17 автоматических тестов UART/HTTP прошли. C++ peer собирается с активными assert
  и использует реальное ядро транспорта, адаптер и текущую модель FLProg_WebUI.
- Проверены CRC/COBS, все длины payload 0..256 на Python, шум/переполнение,
  порционная передача C++ с доступными 7 байт TX и бюджетом 8 байт за pool,
  типы, UTF-8, запись/политика диапазонов, системные и command-only каналы,
  повтор номера запроса, pending-команда, перезапуск C++ peer и новая синхронизация.
- Потерянный ответ не вызывает повтор команды; повреждённый кадр не исполняется.
- HTTP проверяет Host/Origin, специальный заголовок команды, размер/типы,
  сеанс из чтения, ID сайта; выход за папку и выдача bridge.json запрещены.
- 99 существующих тестов редактора, экспорта, проверки совместимости и менеджера
  прошли после добавления кнопки запуска и метода commandPending().
- Все три EXE собраны PyInstaller 6.10.0, Python 3.8; мост включает pySerial 3.5.
- Готовый EXE моста проверен отдельно от исходников: чтение 25, команда 30.5,
  повторное чтение, accepted=true/confirmed=false, PING при простое.
- Через встроенный браузер выполнено 25 → 31.25, получено сообщение приёма,
  затем прочитано 31.25. Это **демо без физического контроллера**.
- Проверены окна моста и менеджера, запуск отдельного моста кнопкой менеджера.
- В EXE редактора кнопка «Мост связи» запустила отдельный EXE без открытия COM.
- Все 21 профиль менеджера перенесены из r16 без изменения BIN/загрузчиков.

## Контрольная компиляция STM32

FLE4D-30MT/F407, FLProg STM32 core 3.0.0. Использован конкретный класс Uart
этой версии ядра, PC7/PC6, 115200. Это выбор для компиляции, не назначение
свободного порта на реальном ПЛК (там UART6 может быть занят консолью).

Минимальный скетч: Flash **19 464 байта**, статическая RAM **2 676 байт**.
В ARM ELF объект `bridge` (Server) занимает **936 байт**, `bridgeUart` — 280,
адаптер `web` — 8, модель — 12, два слота — 136. Это не замер пикового стека
и не разница памяти относительно пользовательского проекта.
BIN помечен compile_check_not_for_flashing и не включается в пользовательский
комплект. Прошивки/загрузчики ПЛК не изменялись.

## Ещё не подтверждено и не реализовано

COM на реальном USB-UART/FLE4D, загрузка CPU и переполнение аппаратного UART,
работа вместе с Ethernet/OTA/Modbus/MQTT, физические DO/AO, полномасштабный WebUI
проект через мост, новый Basic/Professional UART блок, ESP32/8266 шлюз.
Устойчивость под длительной многоклиентской нагрузкой также не измерена.

Пока маршруты WebUI канального API обслуживают один активный запрос. Modbus/MQTT
только зарезервированы и не объявляются доступными устройством. Подключение
после ошибки ручное, команды не восстанавливаются из очереди после reset.
