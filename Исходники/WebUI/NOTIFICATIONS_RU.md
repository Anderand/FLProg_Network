# Уведомления команд и ошибок

25.10.2026. Проверено на FLE4D-30MT / STM32F407VG / W5500,
прошивка **1.0.9-NOTICES**. Результат включён в локальный комплект r11.
Git и GitHub обновляются только по отдельной команде пользователя.

## Что означают этапы

| Этап | Значение |
|---|---|
| Отправляется… | Команда подготовлена, ожидается начало HTTP-запроса |
| Отправлено | Браузер начал запрос записи; подтверждение доставки ещё ожидается |
| Принято контроллером | Получен успешный HTTP-ответ с `queued: true` |
| Подтверждено данными | После ответа выполнено успешное чтение состояния, и выполнено условие подтверждения |

Приём команды и чтение данных сами по себе не доказывают физическое действие
оборудования. Уведомление показывает конкретный канал и его значение.
Смысл кода/текста result определяет программа FBD; уведомление не называет
произвольное значение result успешным выполнением.

## Подтверждение данными

- У полей и переключателей проверяется канал связи `value`, если она задана,
  иначе основной канал виджета. Уставка отправляется в `setpoint`, если есть
  эта связь. Сравнение учитывает тип bool/number/text и точность числового JSON.
- У виджета с `result` проверяется новое значение результата. При связи busy
  подтверждение ожидает busy=false и наблюдавшийся busy-цикл либо изменение result.
  Старый result=true не подтверждает новую команду автоматически.
- Без result подтверждается только чтение значения канала, а не выполнение FBD.
- Снимки до успешного ответа записи не подтверждают команду. Неизменившиеся
  данные учитываются по контракту revision/since после успешного опроса.
- Если данные не подтвердились за 30 секунд, появляется сообщение об отсутствии
  подтверждения. Команда автоматически не повторяется.

У контроллера пока нет идентификатора команды в данных обратной связи.
Поэтому это проверка состояния/перехода, а не гарантия причинной связи
при одновременной работе нескольких операторов. Для ответственных действий
точный идентификатор выполнения нужно предусматривать в контракте FBD.

## Ошибки и восстановление

- Отмена в диалоге происходит до отправки и создаёт отдельное сообщение.
- Неверный ввод, отказ сервера и отсутствие подтверждения приёма показываются
  как ошибки. Ошибка поля сохраняет черновик, действующее значение остаётся рядом.
- При таймауте ответа результат считается неизвестным. Автоматического повтора нет.
- При ошибке опроса связь отмечается потерянной, ожидающие подтверждения снимаются
  с наблюдения с сообщением о неизвестном результате. Восстановление связи
  не превращает такую команду в подтверждённую задним числом.
- Обнаруженный перезапуск ПЛК также прекращает ожидание старого подтверждения.

## Панель

Справа внизу показывается до пяти карточек, новые этапы видны без прокрутки
основной страницы. В карточке сохраняются этапы отправки/приёма/чтения.
Подтверждённые и информационные карточки скрываются через 12 секунд,
ошибки можно закрыть крестиком. Крестик скрывает карточку и не отменяет уже
отправленную команду. Значения паролей в карточках не показываются.

## Что проверено

На FLE4D через настоящий веб:

- Уставка 25→30.5 и все этапы уведомления с чтением setpoint=30.5.
- Отмена команды без увеличения счётчика выполнения.
- Приём команды отдельно от завершения, затем подтверждение result=true.
- Повтор при старом result=true: новая карточка остаётся на приёме до нового
  цикла busy/result; счётчик увеличился только после выполнения.
- Неверная уставка 999: отдельная ошибка ввода.
- Пять карточек и прокрутка панели к последнему этапу.
- Ошибок JavaScript нет; все 19 статических ресурсов совпадают с исходниками
  после gzip-распаковки, число HTTP-маршрутов остаётся 14.

Автотесты отдельно проверяют HTTP 409, отсутствие ACK, таймаут ожидания,
перезапуск, обрыв/восстановление связи, отмену до фактической отправки,
сохранение тайны пароля и защиту от подтверждения старым result.
Всего проходят 26 тестов Python/Node и проверка HTTP-бюджетов.
Физическое отключение кабеля в этом испытании не выполнялось.
