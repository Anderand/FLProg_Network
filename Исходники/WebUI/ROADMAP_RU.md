### Что из K-WEB не переносим напрямую

- Динамический кэш всей HTML-страницы с резервированием около 40 КБ:
  сохраняем descriptor и небольшие ответы вместо такого расхода RAM.
- ID по адресу C++-переменной: сохраняем устойчивые CHANNEL и направления
  Publish/Command/Duplex.
- Обязательные AsyncTCP/ESPAsyncWebServer и ESP LittleFS для STM32:
  сохраняем наш транспорт FLProg_Network. TFT-шрифты из примера не относятся
  к этому Web UI.
- Запись настроек на каждом событии и проверку доступа только после
  загрузки файла: заменяем проектированием отложенного хранения и отказом
  до первой операции записи.
- Буквальное копирование чужих исходников: сначала выяснить условия
  лицензии K-WEB и зависимостей. Включение исходного разбора в документацию
  не означает включение стороннего кода в библиотеку или релиз.

### Очередь оставшихся работ по разбору

1. **Gzip и порционная выдача проверены.** Новое API обслуживает большой
   ресурс из Flash через прежнюю очередь 2048 байт. Существующие bounded-ответы
   сохраняют прежний лимит полного ответа; большие ресурсы требуют нового API.
2. **Интерфейс и навигация:** toast проверен; опрос и фоновые вкладки реализованы (нужна нативная очная проверка);
   восстановление страницы и повтор descriptor проверены на FLE4D; далее оставшиеся настройки полей
   и контейнеров, единая диагностика. Внутренний порядок пока не утверждён.
3. **После — сохраняемые параметры:** общий контракт, отложенная запись
   и платформенные backend.
4. **Отдельно, позднее — SSE и администрирование:** авторизация,
   файловые операции и веб-OTA с соответствующими проверками.

Проверка проекта и офлайн-предпросмотр r7/r8 — последующие улучшения нашего
редактора; не выдаём их за пункты исходного разбора K-WEB. Дополнительные
идеи ниже также отделены от восстановленного списка.

## Этап gzip — выполнен на FLE4D

25.10.2026 выполнены две сравнимые сборки и аппаратная проверка gzip по OTA.
Flash: 137040→130856 байт; статическая RAM: 16112→16112 байт.
[Измерения, проверки и ограничения](GZIP_RU.md). Режим пока опциональный,
общий r9 уже включает gzip. Позднее реализована и проверена порционная выдача
([отчёт](FLASH_STREAM_RU.md)); она включена в опубликованный комплект r13.
Ниже сохранён контрольный список этапа; новый выпуск — отдельной командой.

1. Измерить исходный и сжатый размер HTML/CSS/JS, оценить расход Flash
   и объём передачи на текущем наборе ресурсов.
2. Проверить и при необходимости добавить отправку двоичных данных из
   Flash с точной длиной и заголовком `Content-Encoding: gzip`.
   Текущий вызов `sendProgmem` для текстовых строк сам по себе gzip не даёт.
3. Сжимать статические ресурсы на компьютере при подготовке библиотеки,
   без компрессора и дополнительного рабочего буфера на STM32.
4. Проверить согласование `Accept-Encoding`, заголовки, корректную
   обработку клиента без gzip и распаковку каждого ресурса до исходных байтов.
5. Сохранить ограничение bounded-ответа 2048 байт вместе с заголовками и
   текущий бюджет маршрутов. Новый stream API допускает большее полное тело
   через тот же буфер. Не увеличивать RAM-буфер ради сжатия.
6. Проверить загрузку веба, команды, поля, группы и синхронизацию на FLE4D.
   Сравнить размер BIN и расход RAM с прежней сборкой, а не только размер JS.
7. После проверки подготовить новый EXE/общий комплект по команде
   пользователя. GitHub — только по отдельной команде.

Изменение ресурсов в прошивке потребует пересборки и обновления ПЛК.
Один новый EXE редактора не включает gzip на уже прошитом контроллере.

## Идеи после gzip — порядок не утверждён

## MQTT — динамические подписки (сделано 28.10.2026)

Отдельная задача FLProg_Network по запросу пользователя, не пункт K-WEB.
Вместо четырёх заранее зарезервированных фильтров таблица расширяется по RAM.
SUB_LIMIT=0 снимает фиксированный предел; можно задать добровольный лимит.
Добавлены ошибки лимита/нехватки памяти, счётчик и расход таблицы,

## Правила архитектуры

- `FLProg_Network` содержит только разработческий сетевой API.
- `FLProg_WebUI` содержит общий runtime и адаптеры.
- `.flpui` хранит только дизайн и контракт конкретного проекта.
- project package содержит descriptor и конфигуратор конкретного проекта.
- Изменение layout/темы не меняет FBD-схему; изменение канала является изменением контракта.

## Критерий завершения

Пользователь создаёт проект в редакторе, выбирает публичный транспорт
FLProg_Network, раскладывает виджеты на сетке, экспортирует package/UBL,
связывает универсальные блоки в FLProg и получает адаптивный интерфейс после
прошивки без ручного C++-кода.

## MQTT — обслуживание по периоду и два редактора (28.10.2026)

Сделано локально для r16: MQTT TCP и сервис обслуживаются одним расписанием;
в простое 10 мс (POLL_MS), при обмене 1 мс, чтение/запись порциями до 64 байт.
Блоки вызываются каждый цикл, новые команды будят обслуживание. Подписки
по-прежнему расширяются динамически. Созданы Core/Publish/Subscribe v0.3
в форматах Basic и Professional с одинаковыми входами, выходами и логикой.
Полный C++ стенд, шесть UBI и контрольные сборки F407 проверены.
[Результаты и ограничения](MQTT_PERFORMANCE_RU.md), [применение](MQTT_RU.md).
Следующее испытание: измерить средний/максимальный цикл с реальным брокером
на ПЛК и уточнить результат самостоятельной проверки пользователя в FLProg.
