# Контракт редактора и прошивки — 0.1

`*.flpui` — исходный проект редактора. Это JSON для человека и настольного
приложения, он **не загружается в контроллер**. Кнопка «Экспорт .h» создаёт
`exports/<имя>_generated.h` — статический C++-описатель, пригодный для Arduino.
Кнопка «Установить в библиотеку» записывает тот же контракт в
`FLProg_Network/src/flprogWebUiProject.h`; его использует самостоятельный
Web UI Core при следующей сборке проекта.

Каждый виджет описывает шесть неизменяемых полей: `page`, `id`, `type`, `label`,
`readChannel`, `writeChannel`. Поля каналов — это только идентификаторы, например
`sensors.temperature` или `relay.light`; они не являются фрагментами C++ кода.

## Соответствие будущему пользовательскому блоку

`Web UI Core` будет иметь один экземпляр на HTTP-интерфейс. Его блоки-адаптеры
будут использовать те же строковые идентификаторы:

| Тип виджета | Канал чтения | Канал записи |
|---|---|---|
| indicator | значение датчика | — |
| text | строка состояния | — |
| switch | состояние | новое состояние |
| slider | текущее число | новое число |

Таким образом редактор не генерирует индивидуальный C++ для каждого визуального
элемента и не вторгается в скомпилированную схему FLProg. Он создаёт декларацию,
а пользовательские блоки остаются единственным местом привязки к линиям схемы.

## Уже добавленное ядро библиотеки

`FLProgWebUiCore` доступен через `#include <flprogNetwork.h>`. Он намеренно
отделён от HTTP: `registerWidgets()` принимает экспортированный массив,
`setValue()` публикует значения схемы, `queueWrite()` фиксирует действие
браузера, а `takeWrite()` выдаёт его ровно один раз пользовательскому блоку.
Так внешняя команда не может незаметно изменить переменную схемы.

Минимальное подключение в скетче, который генерирует FLProg:

```cpp
#include <flprogNetwork.h>
#include "my_controller_generated.h"

FLProgWebUiCore webUi;

void setup() {
  webUi.registerWidgets(flprogWebUiWidgets, flprogWebUiWidgetCount);
}

void loop() {
  webUi.setValue("sensors.temperature", temperature);
  String requested;
  if (webUi.takeWrite("relay.light", requested)) {
    relayLight = requested == "1";
  }
}
```

Это пример API, а не замена будущих пользовательских блоков: в финальной
интеграции эти вызовы будут сгенерированы блоками автоматически.

## HTTP API прототипа

После `flpWebUiBegin(FLPROG_WIFI_INTERFACE1)` библиотека запускает самостоятельный сервер
и добавляет начальную страницу с тремя служебными маршрутами:

* `GET /` — стартовая страница FLProg Web UI;
* `GET /flprog-ui/config` — описатели виджетов из конструктора;
* `GET /flprog-ui/state` — JSON с актуальными каналами;
* `POST /flprog-ui/write?channel=relay.light&value=1` — ставит команду в
  очередь, которую схема читает через `takeWrite()`.

Ответ на запись — `202`, а неизвестный канал даёт `404`. Размер ответа состояния
ограничен 1536 байтами по умолчанию (`FLPROG_WEBUI_HTTP_MAX_JSON`), чтобы web UI
не занял общий ограниченный буфер HTTP-сервера на ESP8266.
