# FLProg Web UI Designer: архитектура и варианты интеграции

**Статус:** техническая концепция и рабочий прототип 0.1  
**Адресаты:** Сергей, Энвер  
**Дата:** 10 октября 2026 г.

## 1. Цель

Создать самостоятельный визуальный конструктор web-интерфейсов для проектов
FLProg. Он должен заменить использование штатного Web Interface FLProg в этой
задаче, но сохранить естественный для FLProg способ работы с переменными,
блоками и генерацией Arduino-скетча.

Результат для пользователя:

1. Он визуально собирает страницу контроллера: индикаторы, переключатели,
   ползунки, текстовые поля, страницы.
2. Конструктор создаёт список нужных глобальных переменных FLProg.
3. Пользователь импортирует список в FLProg и строит обычную FBD-логику.
4. В прошивку попадает компактное статическое описание web-интерфейса и
   runtime `FLProg_Network`.
5. Браузер обращается непосредственно к устройству по HTTP; отдельный сервер
   или облако не нужны.

## 2. Главное архитектурное решение

Направление обмена выбрано таким:

```text
Web UI Designer
   │
   ├── *.flpui — исходный проект интерфейса
   ├── *.fvl   — глобальные переменные для импорта в FLProg
   └── flprogWebUiProject.h — статическое описание для прошивки
            │
            ▼
        FLProg
   ├── импорт *.fvl
   ├── FBD-схема и прикладная логика
   └── пользовательские блоки Web UI
            │
            ▼
     Arduino/ESP/RP2040
   └── FLProg_Network + HTTP Web UI runtime
            │
            ▼
          Браузер
```

То есть **источник модели интерфейса — конструктор**, а не уже созданный
проект FLProg. Импорт `.fvl` из FLProg в конструктор остаётся полезной
дополнительной функцией для обратной синхронизации, но не является главным
сценарием.

## 3. Форматы и ответственность компонентов

| Артефакт | Кто создаёт | Для чего нужен |
|---|---|---|
| `*.flpui` | Web UI Designer | Редактируемое описание страниц, виджетов и привязок |
| `*.fvl` | Web UI Designer | Штатный импорт глобальных переменных в FLProg |
| `flprogWebUiProject.h` | Web UI Designer | Компактный C++-описатель страниц/виджетов в прошивке |
| `.flp` | FLProg | FBD-логика, оборудование, переменные, пользовательские блоки |
| `.ino` | FLProg | Генерируемый скетч; вручную не редактируется |

### Формат `.fvl`

Экспорт использует XML-формат FLProg в UTF-16LE с BOM и коллекцию
`FBDVariableTag`. Для виджетов назначаются штатные классы типов:

| Виджет | Тип импортируемой переменной |
|---|---|
| Переключатель | `BooleanDataType` |
| Ползунок | `IntegerDataType` |
| Индикатор | `FloatDataType` |
| Текст | `StringDataType` |

Для одинакового имени создаётся детерминированный UUID, поэтому повторный
экспорт одного проекта не создаёт новый идентификатор переменной.

## 4. Текущее состояние реализации

Рабочая папка конструктора:

`E:\FLP\Flprog_network\web_ui_designer`

Уже реализовано:

- локальный конструктор без Node.js, npm и внешних зависимостей;
- страницы и виджеты `indicator`, `switch`, `slider`, `text`;
- привязки чтения и записи;
- сохранение проекта в `projects/*.flpui`;
- экспорт `.fvl` и автоматическое скачивание файла;
- импорт существующего `.fvl` для выбора переменной в редакторе;
- генерация статического заголовка для библиотеки;
- установка сгенерированного заголовка в
  `FLProg_Network/src/flprogWebUiProject.h`;
- HTTP runtime в `FLProg_Network`, не использующий штатный Web Interface.

Текущий runtime имеет маршруты:

```text
GET  /                    — web-страница устройства
GET  /flprog-ui/config    — описание виджетов
GET  /flprog-ui/state     — текущие значения
POST /flprog-ui/write     — запись значения из браузера
```

## 5. Что ещё необходимо для полноценного сценария

### 5.1. Генерация проектного пользовательского блока

Существующий общий блок с ручным полем имени канала — временная диагностика.
Он не соответствует целевому удобству FLProg: пользователь не должен вручную
вводить строки вроде `relay.light` в нескольких местах.

Реализован экспорт второго артефакта: `*.ubi` — пользовательского блока,
сгенерированного именно для конкретного `.flpui` проекта. Его XML-структура и
уникальность идентификаторов проверяются генератором; следующий обязательный
шаг — импорт в FLProg и тестовая компиляция на реальной схеме.

Пример для проекта с переменными:

```text
Температура      Float, вход блока (FLProg → Web)
Свет             Boolean, вход и выход (FLProg ↔ Web)
Уставка          Integer, вход и выход (FLProg ↔ Web)
Текст статуса    String, вход блока (FLProg → Web)
```

Блок должен содержать понятные русские подписи и не требовать ручной настройки
имён каналов. Имена во внутреннем HTTP-контракте остаются в сгенерированном
заголовке и не становятся частью пользовательской FBD-схемы.

### 5.2. Единый экспорт

Кнопка **«Экспорт для FLProg»** должна выдавать набор:

```text
<имя_проекта>.fvl       — импортировать в FLProg
<имя_проекта>.ubi       — импортировать как пользовательский блок
<имя_проекта>.h         — установить/подключить в библиотеке
README_ИМПОРТ.txt        — три коротких шага для пользователя
```

В дальнейшем это лучше упаковывать в один `.zip` или собственный файл пакета
`.flpui-package`.

### 5.3. Связь с переменными FLProg

Сам `.fvl` добавляет переменные в проект, но не создаёт соединения FBD.
Это нормально: логику соединений должен создавать пользователь в схеме FLProg.

В целевом блоке:

- входы передают значения переменных из FBD в web-интерфейс;
- выходы выдают новые значения, поступившие от браузера;
- выход `NEW` или `CHANGED` сообщает о новом пользовательском действии;
- блок не владеет бизнес-логикой, а только транспортирует значения.

## 6. Варианты интеграции с редактором FLProg

### Вариант A — отдельный конструктор и экспорт (рекомендуемый первый этап)

Конструктор запускается через `launch_designer.cmd` или отдельное приложение.
Обмен с FLProg выполняется через `.fvl` и `.ubi`.

Плюсы:

- не требуется менять исходный код FLProg;
- можно быстро развивать редактор независимо;
- нет риска сломать генерацию скетчей или штатные блоки;
- подходит для передачи внешним пользователям.

Минусы:

- пользователь делает импорт двух файлов;
- нет автоматического открытия конструктора из меню FLProg.

### Вариант B — запуск конструктора командой/блоком FLProg

Добавить в FLProg пользовательскую команду, ссылку или блок, который запускает
`launch_designer.cmd` и передаёт путь текущего `.flp` либо папку проекта.

Плюсы:

- привычная точка входа «из FLProg»;
- не требует глубокого встраивания редактора.

Минусы:

- необходим поддерживаемый механизм расширений или изменение программы FLProg;
- всё ещё потребуется импорт результатов, если API FLProg не позволяет это
  сделать программно.

### Вариант C — плагин/вкладка в FLProg

Встроить Web UI Designer в интерфейс FLProg как редактор проекта.

Плюсы:

- единый UX: переменные, блоки, интерфейс и схема в одном приложении;
- возможна автоматическая синхронизация и импорт.

Минусы:

- требуется официальный API плагинов/редакторов либо доступ к исходному коду
  FLProg;
- это отдельный крупный проект с привязкой к версиям FLProg.

### Вариант D — нативный тип проекта в FLProg

Добавить в формат `.flp` сущность Web UI, редактор и кодогенератор прямо в
ядро FLProg.

Плюсы:

- наилучшая интеграция;
- отсутствует экспорт/импорт между отдельными приложениями.

Минусы:

- возможно только при совместной разработке с авторами FLProg;
- самый дорогой по реализации и сопровождению вариант.

## 7. Рекомендуемая дорожная карта

1. **Закрыть прототипный контур.** Проверить импорт сгенерированного `.fvl` в
   FLProg на ESP8266 и ESP32.
2. **Проверить проектный `.ubi` в FLProg.** Импортировать блок и убедиться,
   что его типизированные входы/выходы корректно появляются в FBD-схеме.
3. **Собрать пакет экспорта.** Одна команда и понятная инструкция импорта.
4. **Регрессия runtime.** HTTP, Wi-Fi, Ethernet/W5500, ESP8266, ESP32, RP2040;
   оценка памяти и устойчивости соединений.
5. **UX редактора.** Группы, стили, диапазоны ползунков, проверка типов,
   предпросмотр телефона/ПК, локализация RU/EN.
6. **Обсудить API-интеграцию с FLProg.** Выбрать вариант B, C или D только при
   наличии поддерживаемой точки расширения.

## 8. Вопросы для Сергея и Энвера

1. Может ли FLProg открыть внешний редактор из меню, блока или команды и
   передать ему путь текущего проекта?
2. Есть ли публичный API для программного импорта `.fvl` и `.ubi` в текущий
   `.flp`?
3. Можно ли зарегистрировать собственный тип редактора/плагин-вкладку без
   модификации ядра FLProg?
4. Какой формат пользовательского блока предпочтителен для генерации:
   один проектный `.ubi` или несколько малых блоков по виджетам?
5. Можно ли включать сгенерированный заголовок в папку проекта FLProg, а не
   перезаписывать общий файл библиотеки? Это предпочтительно для параллельных
   проектов.

## 9. Принципы, которые не меняем

- Web UI не использует стандартный Web Interface FLProg.
- `FLProg_Network` остаётся транспортным runtime, без тяжёлого JSON-парсера на
  устройстве.
- Конструктор не изменяет вручную сгенерированный `.ino`.
- Переменные и прикладная логика принадлежат FLProg/FBD; интерфейс не заменяет
  FBD-схему.
- Экспорт должен быть воспроизводимым, компактным и пригодным для передачи
  другому пользователю.
- Сгенерированный код, исполняемый в каждом проходе FBD-цикла, не создаёт
  временные объекты `String` и не выполняет динамическое выделение памяти.
  Это обязательно для устойчивости ESP8266; преобразование HTTP-значений
  выполняется только при поступлении фактической команды.

## 10. Целевая изоляция проектов

Единый файл `FLProg_Network/src/flprogWebUiProject.h` признан временным и не
должен использоваться далее: он перезаписывается при работе со вторым проектом.

Целевая структура:

```text
<папка FLProg-проекта>/webui/
  <project-id>.flpui              — исходный дизайн
  <project-id>.fvl                — список переменных
  <project-id>.ubi                — однократно импортируемый конфигуратор

<sketchbook>/libraries/FLProg_WebUI_<project-id>/
  library.properties
  src/<project-id>_descriptor.h   — компилируемый артефакт только этого проекта
```

`FLProg_Network` остаётся чистой разработческой библиотекой: в ней находятся
только исходный runtime, общие пользовательские блоки и документация
разработчиков. В неё не записываются `.flpui`, `.fvl`, `.ubi` или заголовки
конкретных пользовательских проектов.

`.flpui` остаётся рядом с проектом пользователя. Для компиляции создаётся
отдельная Arduino-библиотека-пакет `FLProg_WebUI_<project-id>`; она принадлежит
только одному проекту и может безопасно обновляться дизайнером.

Конфигуратор `.ubi` импортируется один раз и содержит только подключение
постоянного `descriptor.h`. Он не содержит список входов/выходов виджетов.
Для связи FBD и UI используются стабильные универсальные блоки публикации и
команд по типам. Поэтому изменение страницы, подписи, расположения, стиля или
диапазона виджета требует только обновить `descriptor.h` и перепрошить плату;
переимпортировать блок и пересоединять FBD-схему не требуется. Новый `.fvl` и
новые FBD-связи нужны лишь при изменении состава или типов переменных.
